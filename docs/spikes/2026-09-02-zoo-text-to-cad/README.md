# Spike: Zoo text-to-CAD against the NEMA 17 bracket

**Date:** 2026-09-02 · **Status:** complete. Baseline measured, two live Zoo
generations captured, STEP exported and measured against the kernel ·
**Owner:** workbench

## The question

FORGE proposes geometry as a handful of primitives (`box`, `cylinder`, `cone`,
`sphere`, `tube`, `plane`) with dimensions the model invents. The provenance
banner says, correctly, that no CAD kernel exists in this deployment.

Zoo returns **STEP** — a real B-Rep solid — and, in the current API, **KCL**
source, which is parametric and editable.

So: *is Zoo's output good enough on our own reference part to be worth the
integration, and what exactly would the integration be?*

Reproduce everything here with:

```bash
python3 analyse.py            # the baseline table below
python3 analyse.py --zoo-spec # re-derive Zoo's API surface (network)
```

---

## Result 1 — the API I recommended does not exist any more

I told you Zoo had "two endpoints, generate and edit". That was true of the
December 2023 launch and is **stale**. Derived from the published OpenAPI
document (`KittyCAD/kittycad.go@main`, Zoo API 0.1.0), the entire text-to-CAD
surface today is:

```
GET       /user/text-to-cad          list parts you have generated
GET       /user/text-to-cad/{id}     read one back
POST      /user/text-to-cad/{id}     submit FEEDBACK on a response
```

`analyse.py --zoo-spec` prints `REST generation endpoint present: False`. There
is no `POST /ai/text-to-cad/{output_format}`. Generation now happens over:

```
GET   /ws/ml/copilot          websocket — the Zookeeper agent
GET   /ws/ml/reasoning/{id}   websocket
POST  /ml/kcl/completions     REST, returns KCL SOURCE (not geometry)
```

**Why this matters for the decision:** the integration is no longer "POST a
prompt, poll an id, download a STEP". It is either a stateful websocket session
with a message protocol (`MlCopilotClientMessage` has 7 variants,
`MlCopilotServerMessage` has 14), or a code-completion call whose output has to
be *executed* by a KCL engine before it is geometry. That is a materially larger
piece of work than what I described, and you should re-price it before deciding.

The read path is still worth knowing: a `text_to_cad` response carries `outputs`
(a map of path → **base64 file**), `output_format` ∈ `fbx, glb, gltf, obj, ply,
step, stl`, plus `code`, `kcl_version`, `model_version`, and a `status` of
`queued | uploaded | in_progress | completed | failed`. So a part generated by
any means can be pulled back as STEP **and** as parametric source.

## Result 2 — the baseline is worse than I had assumed, and I can prove it

Four runs of the **identical** prompt, empty history, nothing else varied
(`data/forge-baseline-runs.json`):

| run | ms | parts | plate face | thick | boss ⌀ | rib modelled as |
|----:|---:|------:|-----------:|------:|-------:|-----------------|
| 0 | 14673 | 4 | 50 | 5 | 20 | cone |
| 1 | 13098 | 4 | 50 | 5 | 23 | cone |
| 2 | 13346 | 4 | 42 | 3 | 28 | cone |
| 3 | 14681 | 4 | 50 | 3 | 16 | cylinder |

Scored against the published standard (42.3 mm face, 31 mm bolt square, ⌀22 mm
pilot boss, ⌀5 mm shaft) — stated in `analyse.py` rather than taken from any
model, so nothing grades its own homework:

- **Plate face 42–50 mm.** One run in four lands within ±0.5 mm of 42.3.
- **Plate thickness 3–5 mm** — a 67% spread on the same sentence.
- **Boss ⌀ 16, 20, 23, 28 mm.** The standard pilot boss is 22. The four runs
  bracket it and none of them hit it for a stated reason.
- **The rib is not a rib.** Across five observed runs it has been a `cone`, a
  `cylinder`, and (in an earlier session) a `triangle-prism`. A stiffening rib is
  none of those; the primitive set has no wedge, so there is no correct answer
  available to the model.

Two failures are worse than imprecision, because they are the interface
asserting something untrue:

- **A fabricated standard.** Run 0's assumptions state *"centered NEMA 17 bolt
  pattern (holes at ±20.5 mm on both axes)"*. That is a 41 mm pattern. NEMA 17 is
  31 mm square. It is wrong, it is specific, and it is in the field whose entire
  job is honesty. Runs 1 and 3 state 31 mm correctly — so the same prompt
  produces both the right figure and a fabricated one.
- **Text contradicting geometry.** Run 3's assumptions say *"conical frustums"*
  while both ribs are emitted as `shape: cylinder` — with `radius: 0`, a
  degenerate solid. The parts list, the assumptions and the render disagree with
  each other in one reply.

The provenance banner covers "not stress-analysed". It does not cover "this
dimension is invented" or "the number I quoted for a published standard is
wrong", and those are the two that were actually observed.

## What this changes about the question

The spike started as *"is Zoo's geometry better?"* and the baseline data moves it.
The problem is not that our cylinders are ugly. It is that:

1. the same prompt produces different parts each time, so nothing downstream can
   depend on a dimension; and
2. the model states standards figures as fact, and sometimes they are wrong.

Zoo's STEP output addresses (1) if and only if it is more repeatable — which is
exactly the thing left to measure. Neither Zoo nor anything else addresses (2);
that is ours to fix, and it is cheaper than an integration.

## Result 3 — one live Zoo generation, and it is not close

Key supplied 2026-09-02. `GET /user` → 200, account on the **free** plan with
zero prior generations, so nothing here is inherited from an earlier session.

Getting a turn out of it took three findings, each of which would have been an
afternoon for whoever integrated this:

1. `POST /ml/kcl/completions` returns `{"completions":[]}` — for a natural
   language prompt, a comment plus a sketch stub, a comment alone, and an
   assignment prefix. Four shapes, four empty arrays. The REST ML path cannot
   generate on this account.
2. The websocket is the only route. `wss://api.zoo.dev/ws/ml/copilot` with an
   `Authorization: Bearer` header returns `101` and immediately sends
   `session_data` and `conversation_id`.
3. **A browser cannot use it.** The WebSocket API has no header hook, and the
   two header-free forms — `?token=` and `Sec-WebSocket-Protocol` — are refused
   with *"Please send `{ headers: { Authorization: ... } }` over this
   websocket"*. That in-band frame was accepted once in an early probe and
   **refused on every attempt since**, including a byte-identical replay, so it
   is recorded as unreliable rather than as working. Node's global `WebSocket`
   is therefore unusable here; the run below uses the `ws` package, which can
   set headers.

Same prompt as the four baseline runs. 62 frames, 52 of them reasoning
(`data/zoo-run-1/reasoning.json`), producing `data/zoo-run-1/main.kcl` — 189
lines of KCL.

### The figures

Mid-run, unprompted, it states its own reference:

> "I'm using the standard NEMA 17 face pattern — **42.3 mm frame, 31 mm square
> bolt spacing, and a nominal 22 mm pilot** — with practical clearances for a
> generic stepper."

All three correct. It then searched a corpus of samples, and considered fetching
the manufacturer datasheet *specifically so it could cite it*. What reached the
file:

| figure | Zoo | ours, 4 runs | standard |
|---|---|---|---|
| bolt square | `motorHolePitch = 31mm` ✓ | fabricated once as ±20.5 mm (=41), correct twice, absent once | 31 mm |
| pilot bore | `pilotClearanceDiameter = 23mm` ✓ (22 + 1 clearance, stated) | 16 / 20 / 23 / 28 — brackets it, never for a stated reason | ⌀22 mm |
| fastener clearance | `motorHoleDiameter = 3.5mm` ✓ | not modelled | M3 → 3.4–3.5 mm |
| plate face | `plateSize = 60mm`, presented as a **choice** | 42 / 50 / 50 / 50, presented as matching the standard | 42.3 mm face |

The last row is the one that matters. Zoo picked 60 mm and did not claim it was
the standard. We picked 50 mm and *said it matched the NEMA 17 footprint*.

### The shape of the output

- **16 named parameters**, every one carrying a unit (`60mm`, not `60`)
- **28 constraint equations** — `coincident` ×12, `horizontalDistance` ×11,
  `verticalDistance` ×11, `radius` ×6, `fixed` ×1 — a genuinely constrained
  sketch, so changing `plateSize` moves the geometry rather than breaking it
- `@settings(defaultLengthUnit = mm, kclVersion = 2.0)` — units and language
  version pinned in the artefact
- the ribs are **constrained sketched rectangles**, extruded — 52 × 6 mm, 4 mm
  deep, each with `horizontal`/`vertical` constraints and its offset expressed as
  `verticalDistance([ORIGIN, …]) == ribOneYOffset`

  **Correction to an earlier draft of this document**, which said Zoo modelled
  the ribs as features "ours cannot be, because there is no wedge in the
  primitive set". Zoo's ribs are rectangular prisms, and our `box` primitive
  represents those perfectly well. Read from the KCL, not assumed. The real
  difference is not the shape: it is that Zoo's rib is *constrained and named*,
  and ours is a loose primitive with an invented rotation — which is why the same
  prompt has given us a cone, a cylinder and a triangle-prism for it.

Ours has zero named parameters, zero constraints, and no units on any number —
`{"width": 50}` with `"units": "mm"` declared once for the whole assembly.

### What it cost

Latency is the trade. Ours: **13–15 s**, four runs. Zoo: still working at
**180 s** when the harness cut it off — mid-lint, after writing the KCL. It is
not a conversational latency and it is not trying to be.

### STEP: obtained, and it is a real B-Rep

Not from the copilot. `MlCopilotTool` enumerates exactly four tools —
`edit_kcl_code`, `text_to_cad`, `mechanical_knowledge_base`, `web_search` —
**none of which exports**. Two attempts confirmed it behaviourally before the
schema was read: resuming the conversation with *"Export the part as a STEP
file"* and a 600 s timeout made the agent rebuild the entire part from scratch
and export nothing, because **project state is client-side** (`current_files`
and `project_name` on the `user` message; a client that sends neither hands the
agent an empty project every turn). No timeout fixes that.

Export lives in Zoo's own CLI, which drives the modeling engine
(`KittyCAD/cli` v0.2.193, `zoo-aarch64-apple-darwin`, 56 MB, sha256 verified
against the published checksum):

```bash
zoo kcl export --output-format=step main.kcl .   # -> output.step, 55 400 bytes
```

`data/zoo-run-1/bracket.step`. It is not a mesh:

| entity | count |
|---|---|
| `MANIFOLD_SOLID_BREP` | 1 |
| `CLOSED_SHELL` | 1 |
| `ADVANCED_FACE` | 35 |
| `PLANE` / `CYLINDRICAL_SURFACE` / `CIRCLE` | 18 / 6 / 54 |
| `TRIANGULATED` / `TESSELLATED` | **0** |

Schema `AP242_MANAGED_MODEL_BASED_3D_ENGINEERING_MIM_LF`. A closed, watertight
solid built from analytic surfaces. **This closes the last unproven claim in this
document.**

### Measured, by the kernel rather than by reading source

`measure-step.sh` against the exported STEP, plus the CLI against the KCL — two
independent paths that agree:

| quantity | value | how |
|---|---|---|
| solid extents | **60.000 × 60.000 × 11.000 mm** | parsed from the STEP's `CARTESIAN_POINT`s |
| volume | **19.386097 cm³** | `/file/volume` on the STEP *and* `zoo kcl volume` — identical to 8 s.f. |
| surface area | 95.331 cm² | `/file/surface-area` |
| centre of mass | (30.000, 30.000, 1.532) mm | `/file/center-of-mass` |
| mass, 6061 | 52.34 g | `/file/mass`, 2700 kg/m³ |

The extents match the source exactly: `plateSize = 60mm` → X and Y span 60.000;
`plateThickness = 5mm` above and `bossDepth = 6mm` below → Z from −6.000 to
+5.000. Centre of mass at the dead centre of the plate. **The parametric source
and the produced solid agree**, which is the property the whole comparison turns
on and which could not be checked until a solid existed.

#### A false alarm worth recording

`zoo kcl bounding-box` reported **110 × 110 × 13 mm**, which reads as a part
wildly larger than its own parameters. It is not. That command measures
"everything in a KCL file" — its own help says so — including sketches and
construction planes, which carry no mass and are not exported. Volume, centre of
mass and the STEP's own points all say 60 × 60 × 11. The lesson is the one this
spike keeps repeating: **measure the artefact, not a convenient proxy for it.**
Had this been reported from the `bounding-box` number alone it would have been a
fabricated defect.

## Result 4 — repeatability, which is the number that actually decides this

`python3 analyse.py --zoo-runs`. Two independent Zoo generations of the same part:

| concept | run 1 | run 2 | stable? |
|---|---|---|---|
| bolt square | 31 mm | 31 mm | **yes** |
| pilot clearance ⌀ | 23 mm | 23 mm | **yes** |
| bolt clearance ⌀ | 3.5 mm | 3.6 mm | varies (both valid M3 clearance) |
| plate size | 60 mm | 72 mm | varies |
| plate thickness | 5 mm | 6 mm | varies |
| boss ⌀ | 32 mm | 56 mm | varies |
| rib length | 52 mm | 35 mm | varies |

Zoo's parameter *names* change between runs too (`motorHolePitch` →
`motorBoltSpacing`), which is why `analyse.py` compares by concept; comparing by
identifier reports "everything changed" and hides the finding.

**The split is the finding.** What Zoo takes from the standard is stable across
runs. What Zoo chooses is not — and it never claims the chosen figures are
standard. Ours varies both, and presents the varying ones as conformance:
"50x50x5 mm with centered NEMA 17 bolt pattern".

That is the same distinction the fabricated-standard fix draws, arriving
independently from the outside. It is the strongest argument in this document
that the distinction is real and not a piece of local philosophy.

Caveat, stated because it weakens the result: run 2 was a *resumed* conversation
answering "export it", not a clean repeat of the original prompt. It rebuilt the
part from scratch, so it is an independent generation — but it is not a
controlled N=2. Two clean repeats would settle it.

would not, the endpoint has no export tool and the timeout was never the
constraint. The route that worked is the CLI.

## The recommendation

**Do not integrate Zoo now. Take the one idea it proves, which is already taken.**

What the spike actually established:

- Zoo produces a real AP242 B-Rep from one sentence, whose solid matches its own
  parameters exactly, in ~3 minutes.
- The figures it takes from a standard are **stable across runs**; the figures it
  chooses are not, and it never presents a chosen figure as a standard one.
- Getting there needs a websocket a browser cannot open, a client that carries
  project state, and a 56 MB CLI to export. That is not a component you drop in;
  it is a subsystem, and it replaces the thing our product is currently *for*.

Against that, the defect it exposed in us — quoting a standard's figure and
getting it wrong — is fixed, in a day, with no dependency:
`docs/bugfix/2026-09-02-fabricated-standards-figures.md`.

Revisit when the product needs a manufacturable artefact rather than a shape to
talk about. At that point the work is real and this document is the estimate.

## What it already changed

Nothing about Zoo fixes our second defect — quoting a standard's figure wrongly —
and waiting for an integration to fix it would have been the wrong order. That is
now fixed independently and is in `docs/bugfix/2026-09-02-fabricated-standards-figures.md`.

Zoo is also the existence proof for the fix's ceiling: it did not merely avoid
the wrong number, it **named its source, searched a corpus, and wanted to cite a
datasheet**. Our detector labels a recalled figure as unchecked. Zoo checks.
